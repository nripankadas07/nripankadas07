# Star Growth Playbook

Last updated: June 13, 2026.

This playbook is for earning real stars, follows, forks, issues, and discussions
without fake adoption claims or spam. The profile already has strong hygiene;
the missing signal is external validation from developers who find the projects
useful.

## Star-Worthy Angles

| Project | Audience | Hook |
|---|---|---|
| PatchGym | AI tooling builders, eval engineers, coding-agent researchers | Mine real Git commits into hidden-test coding-agent tasks locally. |
| SpecForge | Developers planning portfolio projects or AI workflow products | Turn high-star repo patterns into a spec workflow and README blueprint. |
| ProofDeck | Teams reviewing AI-assisted changes | Package run evidence into static bundles that can be inspected later. |
| TraceWeave | Agent framework builders and reliability engineers | Find loops, tool churn, drift, and risky handoffs in local traces. |
| SandboxLedger | Reproducibility and supply-chain-minded developers | Keep an append-only record of local agent runs with verifiable hashes. |
| RAGNeedle | RAG builders and retrieval evaluators | Generate deterministic needle-in-corpus tests with distractor pressure. |

## Profile Conversion Checklist

- Pin the six repositories that match the flagship story: PatchGym,
  TraceWeave, SandboxLedger, ProofDeck, SpecForge, and Context Crucible or
  RAGNeedle.
- Keep the profile README focused on one identity: local-first infrastructure
  for evaluating, debugging, and hardening coding agents.
- Prefer one clear call to action per project: run the demo, inspect the trace,
  verify the bundle, or export the blueprint.
- Add screenshots or short demo recordings only when they are generated from a
  repeatable local workflow.
- Keep Discussions open on flagship repositories and use Issues for scoped,
  reproducible work.
- Do not create fake adoption badges, fake package download counts, or inflated
  benchmark claims.

## Launch Sequence

1. **Week 1: SpecForge demo launch**
   - Share the live demo and source.
   - Lead with the problem: choosing a GitHub-profile project from real OSS
     signals is noisy, and SpecForge turns that into a repeatable spec workflow.
   - Ask for feedback on scoring weights, blueprint format, and workflow nodes.

2. **Week 2: PatchGym technical launch**
   - Share a run artifact, manifest, and hidden-test story.
   - Lead with the harder claim: coding-agent evaluation should be reproducible
     and inspectable, not judged by screenshots.
   - Invite comparisons against existing benchmark workflows.

3. **Week 3: Evidence stack launch**
   - Show the PatchGym -> TraceWeave -> SandboxLedger -> ProofDeck flow.
   - Lead with auditability: a run should leave a trace, ledger entry, and static
     review deck.
   - Ask for integration ideas from people building agent harnesses.

4. **Ongoing: One useful artifact per week**
   - Publish a short technical note, demo recording, comparison table, or
     reproducible example.
   - Link to one repository only per post.
   - Reply to feedback with code changes, docs changes, or issues.

## Weekly Metrics

Track only signals that show real pull:

- stars per flagship repository;
- forks on PatchGym, SpecForge, ProofDeck, and TraceWeave;
- GitHub profile views if available;
- Discussions opened by other people;
- issues opened with reproducible feedback;
- external posts that produce meaningful replies;
- cloned demo runs or user-shared screenshots.

## What Not To Do

- Do not buy stars, trade stars, or use engagement pods.
- Do not mass-DM developers.
- Do not post the same link repeatedly across communities.
- Do not overstate production use, benchmark dominance, or adoption.
- Do not create dozens of empty issues just to make repositories look active.

The durable strategy is simple: make the projects useful, show the evidence,
ask for specific feedback, and turn feedback into visible improvements.
